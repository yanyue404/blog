适配器模式

适配器模式的作⽤是解决两个软件实体间的接⼝不兼容的问题。使⽤适配器模式之后，原本 由于

接⼝不兼容⽽不能⼯作的两个软件实体可以⼀起⼯作。 适配器的别名是包装器(wrapper)，这是⼀

个相对简单的模式。在程序开发中有许多这样的 场景:当我们试图调⽤模块或者对象的某个接⼝

时，却发现这个接⼝的格式并不符合⽬前的需求。 这时候有两种解决办法，第⼀种是修改原来的

接⼝实现，但如果原来的模块很复杂，或者我们拿 到的模块是⼀段别⼈编写的经过压缩的代码，

修改原接⼝就显得不太现实了。第⼆种办法是创建 ⼀个适配器，将原接⼝转换为客户希望的另⼀

个接⼝，客户只需要和适配器打交道。

典型例子：

  • 港式插头转换器，港式的电器插头比大陆的电器插头体积要大一些。
  • 电源适配器：电压转换，电源适配器使笔记本电脑在 100V~240V 的电压之
  • 内都能正常工作
  • USB 转接口

其他相似的设计模式

适配器模式是一对相对简单的模式。在本书提到的设计模式中，有一些模式跟适配器模式的 结构非常相似，比如装饰者模式、代理模式和外观模式）。这几种模式都属于"包 装模式"，都是由一个对象来包装另一个对象。区别它们的关键仍然是模式的意图。

  • 适配器模式主要用来解决两个已有接口之间不匹配的问题，它不考虑这些接口是怎样实现的，也不考虑它们将来可能会如何演化。适配器模式不需要改变已有的接口，就能够使它们协同作用。
  • 装饰者模式和代理模式也不会改变原有对象的接口，但装饰者模式的作用是为了给对象增加功能。装饰者模式常常形成一条长的装饰链，而适配器模式通常只包装一次。代理模式是为了控制对对象的访问，通常也只包装一次。
  • 外观模式的作用倒是和适配器比较相似，有人把外观模式看成一组对象的适配器，但外观模式最显著的特点是定义了一个新的接口。

通俗的方式理解适配器和装饰器的区别

装饰器：原有功能没有或不完善，提供某种新功能，比如网页新增模块、功能组合，sendTD (包装这个方法作为统一的埋点发送方式)

适配器：原有功能是好的，适配某种新平台，比如网页兼容性适配不通的浏览器，sendTd（方法不变的情况下适配新的神策埋点平台）

grok3 的回答

在一个 Vue 项目中，当多个页面（假设有 50 个路由）共用同一个 Pinia store，并且需要处理既有公共结构又有页面特定差异的 calculatorData 和 insuredFormData 时，设计一个可维护、可扩展的 store 和页面关系非常重要。以下是一个详细的设计方案，旨在平衡公共逻辑和私有逻辑的维护性，同时优化代码复用和扩展性。

设计目标

  1. 公共结构复用：将 calculatorData 和 insuredFormData 的公共字段和逻辑提取到 store 中，避免重复定义。
  2. 私有差异隔离：允许每个页面根据路由注入特定的字段或逻辑，保持灵活性。
  3. 易于维护：通过模块化设计减少耦合，方便新增路由或修改现有逻辑。
  4. 性能优化：避免不必要的数据冗余或计算开销。

设计方案

1. Store 设计：分层结构 + 动态注入

将 store 的状态分为公共部分和页面特定部分，并通过动态注入的方式支持差异化需求。

// store/insure.js
import { defineStore } from 'pinia'
import { computed, reactive } from 'vue'

// 定义公共的基础结构
const defaultCalculatorData = {
  baseAmount: 0,
  rate: 1.0
  // 其他公共字段...
}

const defaultInsuredFormData = {
  name: '',
  age: 0
  // 其他公共字段...
}

// 创建 store
const useInsureStore = defineStore('insure', {
  state: () => ({
    calculatorResult: {}, // 测算结果
    insureData: {}, // 核保结果
    // 公共数据基础结构
    baseCalculatorData: reactive({ ...defaultCalculatorData }),
    baseInsuredFormData: reactive({ ...defaultInsuredFormData }),
    // 页面特定数据（动态注入）
    pageSpecificData: reactive({ calculator: {}, insured: {} })
  }),

  getters: {
    // 合并公共和页面特定的 calculatorData
    calculatorData(state) {
      return {
        ...state.baseCalculatorData,
        ...state.pageSpecificData.calculator
      }
    },
    // 合并公共和页面特定的 insuredFormData
    insuredFormData(state) {
      return {
        ...state.baseInsuredFormData,
        ...state.pageSpecificData.insured
      }
    }
  },

  actions: {
    // 初始化页面特定数据
    initPageData(routeName, specificData = {}) {
      const { calculator = {}, insured = {} } = specificData
      this.pageSpecificData.calculator = { ...calculator }
      this.pageSpecificData.insured = { ...insured }
      // 可选：根据 routeName 加载特定的默认值或逻辑
    },

    // 重置页面特定数据
    resetPageData() {
      this.pageSpecificData.calculator = {}
      this.pageSpecificData.insured = {}
    },

    // 保单测算
    async reqCalculator() {
      const params = this.calculatorData
      // 调用 API，更新 calculatorResult
      this.calculatorResult = await apiReqCalculator(params)
    },

    // 核保
    async reqDispatcher() {
      const params = this.insuredFormData
      // 调用 API，更新 insureData
      this.insureData = await apiReqDispatcher(params)
    }
  },

  persist: {
    key: 'pinia',
    storage: window.sessionStorage
  }
})

export default useInsureStore

关键点解释：

  • baseCalculatorData 和 baseInsuredFormData：存储所有页面共享的公共字段。
  • pageSpecificData：存储页面特定的字段，通过 initPageData 动态注入。
  • getters：动态合并公共和特定数据，提供统一的访问接口。
  • reactive：确保数据的响应性。

2. 页面内部设计：路由驱动 + 组合式 API

每个页面通过路由名称动态注入特定数据，并在组件中通过 useInsureStore 获取合并后的数据。

// pages/PageA.vue
<script setup>
import { useInsureStore } from '@/store/insure';
import { useRoute, onBeforeMount } from 'vue-router';

const route = useRoute();
const store = useInsureStore();

// 页面特定的数据结构
const pageSpecificData = {
  calculator: {
    extraFieldA: 100, // PageA 特有字段
  },
  insured: {
    customFieldA: 'specific', // PageA 特有字段
  },
};

onBeforeMount(() => {
  // 初始化页面特定数据
  store.initPageData(route.name, pageSpecificData);
});

// 使用合并后的数据
const calculatorData = computed(() => store.calculatorData);
const insuredFormData = computed(() => store.insuredFormData);

// 提交测算或核保
const handleSubmit = () => {
  store.reqCalculator();
  store.reqDispatcher();
};
</script>

<template>
  <div>
    <input v-model="calculatorData.baseAmount" />
    <input v-model="calculatorData.extraFieldA" />
    <input v-model="insuredFormData.name" />
    <input v-model="insuredFormData.customFieldA" />
    <button @click="handleSubmit">提交</button>
  </div>
</template>

关键点解释：

  • pageSpecificData：定义页面独有的字段。
  • initPageData：在页面挂载时注入特定数据。
  • computed：通过 getter 获取合并后的数据，避免直接操作 store。

3. 路由切换时的清理逻辑

为了避免页面间数据污染，需要在路由切换时重置页面特定数据。可以在全局路由守卫中处理：

// router/index.js
import { createRouter } from 'vue-router'
import { useInsureStore } from '@/store/insure'

const router = createRouter({
  // 路由配置...
})

router.beforeEach((to, from, next) => {
  const store = useInsureStore()
  // 重置页面特定数据
  store.resetPageData()
  next()
})

export default router

4. 可扩展性优化：配置文件化

当路由数量达到 50 个时，手动在每个页面定义 pageSpecificData 会变得繁琐。可以引入一个配置文件来管理所有页面的特定数据。

// config/pageData.js
export const pageDataMap = {
  'page-a': {
    calculator: { extraFieldA: 100 },
    insured: { customFieldA: 'specific' },
  },
  'page-b': {
    calculator: { extraFieldB: 200 },
    insured: { customFieldB: 'unique' },
  },
  // 其他 48 个路由...
};

// pages/PageA.vue
<script setup>
import { useInsureStore } from '@/store/insure';
import { useRoute, onBeforeMount } from 'vue-router';
import { pageDataMap } from '@/config/pageData';

const route = useRoute();
const store = useInsureStore();

onBeforeMount(() => {
  store.initPageData(route.name, pageDataMap[route.name] || {});
});

const calculatorData = computed(() => store.calculatorData);
const insuredFormData = computed(() => store.insuredFormData);
</script>

优点：

  • 将特定数据集中管理，减少页面代码重复。
  • 新增路由只需更新配置文件。

整体架构总结

  1. Store 层：

    • 公共数据：baseCalculatorData 和 baseInsuredFormData。
    • 特定数据：pageSpecificData，通过 initPageData 动态注入。
    • Getter：合并数据，提供统一访问接口。
    • Action：处理业务逻辑（如 API 调用）。

  2. 页面层：

    • 通过路由名称注入特定数据。
    • 使用 computed 获取合并数据，避免直接修改 store。

  3. 路由层：

    • 在切换时重置特定数据，避免污染。

  4. 配置层（可选）：

    • 用 pageDataMap 集中管理特定数据，提升扩展性。

优点

  • 复用性：公共字段和逻辑集中在 store 中，所有页面共享。
  • 隔离性：页面特定数据通过动态注入隔离，互不干扰。
  • 可维护性：模块化设计 + 配置文件化，易于新增或修改页面。
  • 响应性：通过 reactive 和 computed 保证数据实时更新。

应对 50 个路由的扩展性

  • 如果字段差异较小，直接用 pageSpecificData 动态覆盖即可。
  • 如果差异较大，可为每个路由定义独立的子模块（sub-store），通过 Pinia 的模块化功能组合使用。
  • 使用配置文件（pageDataMap）管理特定数据，避免代码分散。

grok3 的回答

你的设想引入适配器模式（Adapter Pattern）是一个非常好的思路，特别是在面对 50 个路由、每个页面输入参数存在差异的情况下。适配器模式可以很好地解耦页面逻辑与 store 的核心逻辑，同时让每个页面的特定需求通过“适配”灵活实现。结合你的代码示例和需求，我会从更全面的架构设计角度优化方案，融入设计模式，并提供一个清晰、可扩展的解决方案。

优化目标

  1. 解耦：将页面特定的参数处理逻辑与 store 的核心逻辑分离。
  2. 灵活性：每个页面通过适配器独立定义参数处理规则。
  3. 可维护性：通过模块化和配置文件减少重复代码，支持快速扩展。
  4. 一致性：保留 store 的公共数据结构和逻辑，确保核心功能统一。

改进后的架构设计

1. Store 核心设计：专注于状态管理和通用逻辑

Store 负责管理公共数据和核心业务逻辑（如 API 调用），不直接处理页面特定的参数调整。

    baseData: reactive({
      calculator: { baseAmount: 0, rate: 1.0 },
      insured: { name: '', age: 0 }
    })
  }),

  getters: {
    calculatorData: (state) => state.baseData.calculator,
    insuredFormData: (state) => state.baseData.insured
  },

  actions: {
    // 测算请求（接受适配后的参数）
    async reqCalculator(params) {
      this.calculatorResult = await apiReqCalculator(params)
      return this.calculatorResult
    },

    // 核保请求（接受适配后的参数）
    async reqDispatcher(params) {
      this.insureData = await apiReqDispatcher(params)
      return this.insureData
    },

    // 更新基础数据
    updateBaseData(type, data) {
      Object.assign(this.baseData[type], data)
    }
  },

  persist: {
    key: 'pinia',
    storage: window.sessionStorage
  }
})

export default useInsureStore

关键点：

  • Store 只负责状态管理和通用 API 调用。
  • 参数的适配逻辑交给外部适配器处理。

2. 适配器模式：页面特定的参数处理

每个页面通过适配器定义自己的参数处理逻辑（beforeCalculate、afterCalculate、beforeDispatcher），适配器将页面的特定需求“翻译”成 store 可用的参数格式。

适配器基类

定义一个通用的适配器接口，方便扩展和规范化。

// adapters/BaseAdapter.js
export class BaseAdapter {
  constructor({ state, getters, rootState }) {
    this.state = state
    this.getters = getters
    this.rootState = rootState
  }

  beforeCalculate(params, templateConfig) {
    return params // 默认不修改
  }

  afterCalculate(res) {
    return res // 默认不修改
  }

  beforeDispatcher(params) {
    return params // 默认不修改
  }
}
页面特定适配器

为每个页面（或路由）实现具体的适配器，继承基类并重写方法。

// adapters/PageAAdapter.js
import { BaseAdapter } from './BaseAdapter'

export class PageAAdapter extends BaseAdapter {
  beforeCalculate(params, templateConfig) {
    // PageA 特定逻辑：调整测算参数
    params.customFieldA = this.state.baseData.calculator.baseAmount * 2
    params.templateId = templateConfig?.id || 'default'
    return params
  }

  afterCalculate(res) {
    // PageA 特定逻辑：处理测算结果
    res.extraResultA = res.total * 0.1
    return res
  }

  beforeDispatcher(params) {
    // PageA 特定逻辑：调整核保参数
    params.specialFieldA = 'PageA-specific'
    return params
  }
}
// adapters/PageBAdapter.js
import { BaseAdapter } from './BaseAdapter'

export class PageBAdapter extends BaseAdapter {
  beforeCalculate(params, templateConfig) {
    // PageB 特定逻辑
    params.customFieldB = this.state.baseData.calculator.rate * 100
    return params
  }
}

3. 适配器注册与管理

通过一个映射表集中管理所有页面的适配器，并根据路由动态加载。

// adapters/adapterMap.js
import { PageAAdapter } from './PageAAdapter'
import { PageBAdapter } from './PageBAdapter'

export const adapterMap = {
  'page-a': PageAAdapter,
  'page-b': PageBAdapter

4. 页面使用适配器

页面通过适配器处理参数，并调用 store 的通用方法。

架构总结

层次结构

  1. Store 层：

    • 管理公共状态和核心业务逻辑。
    • 通过 actions 提供通用接口，接受适配后的参数。

  2. 适配器层：

    • 使用适配器模式为每个页面定义特定的参数处理逻辑。
    • 通过 BaseAdapter 和继承实现一致性和灵活性。
    • 通过 adapterMap 集中管理所有适配器。

  3. 页面层：

    • 调用适配器处理参数，然后传递给 store。
    • 通过响应式绑定直接操作 store 的公共数据。

  4. 路由层：

    • 动态加载适配器，确保页面切换时逻辑正确。

优点

  1. 解耦性：页面特定逻辑与 store 分离，互不干扰。
  2. 扩展性：新增路由只需添加一个适配器类并注册到 adapterMap。
  3. 一致性：公共逻辑在 store 中统一处理，适配器只负责差异化部分。
  4. 可维护性：适配器模块化设计，代码结构清晰。

应对 50 个路由的优化

  • 适配器复用：如果多个页面有相似的参数处理逻辑，可以提取为共享适配器类（如 CommonAdapter），然后在具体适配器中继承和扩展。
  • 配置文件驱动：将适配逻辑参数化，减少适配器类的数量。例如： 
    // adapters/config.js
export const adapterConfig = {
  'page-a': {
    beforeCalculate: (params) => ({ ...params, customFieldA: 100 })
  },
  'page-b': {
    beforeCalculate: (params) => ({ ...params, customFieldB: 200 })
  }
}
    然后动态生成适配器实例，减少代码量。
  • 自动化工具：编写脚本根据路由自动生成适配器模板，提升开发效率。

与你原始设想对比

你的代码已经包含了适配器模式的雏形（beforeCalculate 等函数），我的方案在此基础上：

  1. 引入类结构，规范化适配器接口。
  2. 通过继承和映射表提升扩展性。
  3. 将适配逻辑与 store 分离，保持 store 的纯净性。

提问 3

挺好的，从设计模式的角度出发，还有哪些可以采取的方案，我想减少每个页面的维护心智负担

grok3 的回答

从减少每个页面的维护心智负担（mental overhead）的角度出发，我们需要进一步优化架构，让开发者在面对 50 个路由时，能够尽量少地关注重复性工作或复杂逻辑的实现细节，同时保持代码的可扩展性和一致性。适配器模式已经是一个很好的起点，但我们可以通过引入其他设计模式或架构思路，进一步简化页面层的维护成本。以下是几种可行的方案，从设计模式和架构优化的角度出发：

方案 1：工厂模式 + 数据驱动（Factory Pattern + Data-Driven）

思路

  • 使用工厂模式动态生成适配器，结合数据驱动的方式，将每个页面的特定逻辑定义为配置文件，而不是手写大量适配器类。
  • 页面只需要提供路由名称，工厂根据配置自动生成对应的参数处理逻辑，减少手动编码。

实现

  1. 配置层：定义页面特定逻辑
// config/pageAdapters.js
export const pageAdaptersConfig = {
  'page-a': {
    beforeCalculate: (params, state) => ({
      ...params,
      customFieldA: state.baseData.calculator.baseAmount * 2
    }),
    afterCalculate: (res) => ({
      ...res,
      extraResultA: res.total * 0.1
    }),
    beforeDispatcher: (params) => ({
      ...params,
      specialFieldA: 'PageA-specific'
    })
  },
  'page-b': {
    beforeCalculate: (params, state) => ({
      ...params,
      customFieldB: state.baseData.calculator.rate * 100
    })
  },
  // 默认配置
  default: {
    beforeCalculate: (params) => params,
    afterCalculate: (res) => res,
    beforeDispatcher: (params) => params
  }
}
  1. 工厂类：动态生成适配器
// adapters/AdapterFactory.js
import { pageAdaptersConfig } from '@/config/pageAdapters'

export class AdapterFactory {
  static create(routeName, context) {
    const config = pageAdaptersConfig[routeName] || pageAdaptersConfig.default
    return {
      beforeCalculate: (params, templateConfig) =>
        config.beforeCalculate(params, context.state, templateConfig),
      afterCalculate: (res) => config.afterCalculate(res),
      beforeDispatcher: (params) => config.beforeDispatcher(params)
    }
  }
}
  1. 页面使用
// pages/PageA.vue
<script setup>
import { useInsureStore } from '@/store/insure';
import { useRoute } from 'vue-router';
import { AdapterFactory } from '@/adapters/AdapterFactory';

const route = useRoute();
const store = useInsureStore();
const adapter = AdapterFactory.create(route.name, { state: store.$state });

const handleCalculate = async () => {
  let params = { ...store.calculatorData };
  params = adapter.beforeCalculate(params, { id: 'template-a' });
  const res = await store.reqCalculator(params);
  const adaptedRes = adapter.afterCalculate(res);
  console.log('测算结果:', adaptedRes);
};
</script>

优点

  • 心智负担低：开发者只需维护 pageAdaptersConfig，无需为每个页面编写适配器类。
  • 一致性：工厂统一生成适配器，减少实现差异。
  • 扩展性：新增页面只需添加配置项。

适用场景

  • 页面差异主要集中在参数调整，且逻辑较为简单。
  • 不需要复杂的适配器继承或动态行为。

方案 2：策略模式（Strategy Pattern）

思路

  • 将每个页面的参数处理逻辑定义为独立的策略（Strategy），通过一个上下文类动态选择策略。
  • 页面只需声明所需的策略名称，上下文负责调用对应的处理逻辑。

实现

  1. 定义策略接口和实现
// strategies/strategies.js
export const strategies = {
  pageA: {
    beforeCalculate: (params, state) => ({
      ...params,
      customFieldA: state.baseData.calculator.baseAmount * 2
    }),
    afterCalculate: (res) => ({
      ...res,
      extraResultA: res.total * 0.1
    }),
    beforeDispatcher: (params) => ({
      ...params,
      specialFieldA: 'PageA-specific'
    })
  },
  pageB: {
    beforeCalculate: (params, state) => ({
      ...params,
      customFieldB: state.baseData.calculator.rate * 100
    })
  },
  default: {
    beforeCalculate: (params) => params,
    afterCalculate: (res) => res,
    beforeDispatcher: (params) => params
  }
}
  1. 上下文类
// strategies/StrategyContext.js
import { strategies } from './strategies'

export class StrategyContext {
  constructor(routeName, context) {
    this.strategy = strategies[routeName] || strategies.default
    this.context = context
  }

  beforeCalculate(params, templateConfig) {
    return this.strategy.beforeCalculate(
      params,
      this.context.state,
      templateConfig
    )
  }

  afterCalculate(res) {
    return this.strategy.afterCalculate(res)
  }

  beforeDispatcher(params) {
    return this.strategy.beforeDispatcher(params)
  }
}
  1. 页面使用
// pages/PageA.vue
<script setup>
import { useInsureStore } from '@/store/insure';
import { useRoute } from 'vue-router';
import { StrategyContext } from '@/strategies/StrategyContext';

const route = useRoute();
const store = useInsureStore();
const strategyContext = new StrategyContext(route.name, { state: store.$state });

const handleCalculate = async () => {
  let params = { ...store.calculatorData };
  params = strategyContext.beforeCalculate(params, { id: 'template-a' });
  const res = await store.reqCalculator(params);
  const adaptedRes = strategyContext.afterCalculate(res);
  console.log('测算结果:', adaptedRes);
};
</script>

优点

  • 心智负担低：策略集中管理，页面只需初始化上下文。
  • 灵活性：支持动态切换策略，适合运行时调整逻辑。
  • 复用性：多个页面可共享同一策略。

适用场景

  • 页面逻辑差异较大，且可能需要动态选择策略。
  • 需要在运行时根据条件调整处理逻辑。

方案 3：装饰器模式（Decorator Pattern）

思路

  • 将公共逻辑定义为核心功能，通过装饰器为特定页面添加额外逻辑。
  • 页面只需声明所需的装饰器，减少重复代码。

实现

  1. 核心逻辑
// decorators/CoreHandler.js
export class CoreHandler {
  constructor(context) {
    this.context = context
  }

  beforeCalculate(params) {
    return params
  }

  afterCalculate(res) {
    return res
  }

  beforeDispatcher(params) {
    return params
  }
}
  1. 装饰器实现
// decorators/PageADecorator.js
export class PageADecorator {
  constructor(handler) {
    this.handler = handler
  }

  beforeCalculate(params) {
    params = this.handler.beforeCalculate(params)
    params.customFieldA =
      this.handler.context.state.baseData.calculator.baseAmount * 2
    return params
  }

  afterCalculate(res) {
    res = this.handler.afterCalculate(res)
    res.extraResultA = res.total * 0.1
    return res
  }

  beforeDispatcher(params) {
    params = this.handler.beforeDispatcher(params)
    params.specialFieldA = 'PageA-specific'
    return params
  }
}
  1. 装饰器映射与使用
// decorators/decoratorMap.js
import { CoreHandler } from './CoreHandler'
import { PageADecorator } from './PageADecorator'

const decoratorMap = {
  'page-a': PageADecorator
  // 其他页面装饰器...
}

export const getHandler = (routeName, context) => {
  let handler = new CoreHandler(context)
  const DecoratorClass = decoratorMap[routeName]
  if (DecoratorClass) {
    handler = new DecoratorClass(handler)
  }
  return handler
}
  1. 页面使用
// pages/PageA.vue
<script setup>
import { useInsureStore } from '@/store/insure';
import { useRoute } from 'vue-router';
import { getHandler } from '@/decorators/decoratorMap';

const route = useRoute();
const store = useInsureStore();
const handler = getHandler(route.name, { state: store.$state });

const handleCalculate = async () => {
  let params = { ...store.calculatorData };

  const res = await store.reqCalculator(params);
  const adaptedRes = handler.afterCalculate(res);
  console.log('测算结果:', adaptedRes);
};
</script>

优点

  • 心智负担低：核心逻辑与页面特定逻辑分离，页面只需使用 handler。
  • 可组合性：支持多层装饰器嵌套，灵活扩展。
  • 复用性：公共逻辑在核心类中定义，避免重复。

适用场景

  • 页面逻辑可以分层，且差异部分可以增量添加。
  • 需要支持复杂的逻辑组合。

方案 4：组合式架构（Compositional Architecture）

思路

  • 将参数处理逻辑拆分为小的、可复用的函数组件，页面通过组合这些函数构建所需的逻辑。
  • 减少每个页面的独立代码，复用公共逻辑。

实现

  1. 定义可复用函数
// composables/adapterUtils.js
export const addCustomFieldA = (params, state) => ({
  ...params,
  customFieldA: state.baseData.calculator.baseAmount * 2
})

export const addExtraResultA = (res) => ({
  ...res,
  extraResultA: res.total * 0.1
})

export const addSpecialFieldA = (params) => ({
  ...params,
  specialFieldA: 'PageA-specific'
})
  1. 页面组合逻辑
// pages/PageA.vue
<script setup>
import { useInsureStore } from '@/store/insure';
import { useRoute } from 'vue-router';
import { addCustomFieldA, addExtraResultA, addSpecialFieldA } from '@/composables/adapterUtils';

const store = useInsureStore();

const handleCalculate = async () => {
  let params = { ...store.calculatorData };
  params = addCustomFieldA(params, store.$state);
  const res = await store.reqCalculator(params);
  const adaptedRes = addExtraResultA(res);
  console.log('测算结果:', adaptedRes);
};

const handleDispatch = async () => {
  let params = { ...store.insuredFormData };
  params = addSpecialFieldA(params);
  await store.reqDispatcher(params);
};
</script>

优点

  • 心智负担最低：页面只需组合现成的函数，无需定义类或配置。
  • 高度复用：小函数可跨页面共享。
  • 直观：逻辑显式声明，易于理解和调试。

适用场景

  • 页面差异较小，且逻辑可以拆分为独立的功能块。
  • 开发者更倾向于函数式编程风格。

综合对比与推荐

方案 心智负担 扩展性 复用性 适用场景
工厂模式+数据驱动 低 高 中 参数调整为主，差异简单
策略模式 中 高 高 动态逻辑较多，需运行时切换
装饰器模式 中 高 高 逻辑分层，需增量扩展
组合式架构 最低 中 最高 差异小，可拆分为独立功能块

推荐

  • 如果你的 50 个路由差异较小，且主要集中在参数调整，组合式架构是最优选择，因为它最直观、心智负担最低，且复用性强。
  • 如果差异较大且需要动态性，工厂模式 + 数据驱动是一个折中方案，通过配置文件减少编码量，同时保持扩展性。
  • 如果你希望更强的类型安全和面向对象设计，装饰器模式或策略模式更适合，但需要更多的初始设计工作。

最终建议

结合你的需求（减少页面维护心智负担），我建议从 组合式架构 开始尝试，因为它：

  1. 无需为每个页面定义独立类或配置。
  2. 通过函数复用减少重复代码。
  3. 在 Vue 的组合式 API 生态中天然契合。

如果后续发现差异变复杂，可以逐步引入工厂模式或策略模式。你觉得哪个方向更贴近你的实际场景？或者有什么具体痛点需要进一步解决？
